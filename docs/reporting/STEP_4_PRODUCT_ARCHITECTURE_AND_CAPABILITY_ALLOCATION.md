# 4. Architectural principles and invariants

1. One canonical definition per Metric ID.
2. Shared MoneyMovementQueryService is the only computation path for Phase 1 money metrics.
3. UI, drill-down and export use the same MetricResult and ScopeContext.
4. Current-state balances remain distinct from period activity in later phases.
5. Original-period activity remains distinct from restated metrics in later phases.
6. Sales, payments, returns, refunds and reversals remain distinct.
7. Recognised expenses remain distinct from expense payments in later phases.
8. Purchases, liabilities and supplier payments remain distinct in later phases.
9. Missing cost is never genuine zero without provenance.
10. Complete Gross Profit requires 100 percent coverage.
11. Dependency-gated metrics stay blocked; gate-test execution does not unlock them.
12. Cached values require revision stamps before reconcile claims.
13. Scope chrome is mandatory.
14. Roles affect visibility only; Phase 1 uses existing Owner/Manager report access without entitlement redesign.
15. Historical receipts remain visible after later return or void of the parent invoice.
16. Traceability to SalesPayment and refund rows is mandatory.
17. Aggregation happens in the database for scale.
18. Copy stays understandable to Ghanaian owners and managers without changing economics.

# 5. Present TillFlow reporting architecture

Money received is computed independently in Trading dashboard, weekly digest and today-kpis paths, often excluding payments whose parent invoice is RETURNED or VOID. That contradicts the accepted contract and is the Phase 1 repair target. Refund outflows exist via SalesReturn.refundAmountPence. Unverified statuses are not isolated as a canonical Metric ID today.

# 6. Target architecture

Phase 1 delivers: Payments and Money Received surface and export consuming CanonicalMetricComputationService, which dispatches to MoneyMovementQueryService under ReportingScopeClockService, with DataQualityCompletenessService, ReconciliationService and DrillDownTraceabilityService limited to this vertical. Later phases add other specialised owners without changing Phase 1 formulas.

# 12. Traceability, reconciliation and data-quality architecture

For every Phase 1 Metric ID: DrillDownTraceabilityService exposes SalesPayment rows for money_received* and unverified_legacy_receipts, and SalesReturn refund rows for refund_outflows. ReconciliationService requires identical businessId, branch scope, currency, timezone, period bounds and Metric ID before claiming headline equals detail. DataQualityCompletenessService marks unknown-status amounts UNVERIFIED and excludes them from money_received. Blocked money metrics return UNAVAILABLE UNTIL DEPENDENCY RESOLVED without canonical numbers.

# 13. Snapshot, cache and export architecture

Phase 1 permits only optional stamped MetricResult caching for the Money Received vertical. General SnapshotCacheService, Data-quality centre cache dashboards and immutable digest snapshots are not in Phase 1. CanonicalExportService provides exactly one Money Received export bound to the same ScopeContext and MetricResults as the Payments and Money Received surface.

# 14. Performance and scale architecture

MoneyMovementQueryService aggregates SalesPayment in the database filtered by businessId, receivedAt period, status and optional storeId before returning totals. Detail drill-down is keyset-paginated and must not change totals. Branch filters apply in the aggregate query, not after load. Timeouts must not yield zero. No per-payment Node loops for totals.
